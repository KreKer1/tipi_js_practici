## Асинхронный эксперимент

Перед отдельным контрольным прогоном записан технический прогноз: A, B, C, D, E, F.
Для добавленной микрозадачи G — A, B, C, D, E, G, F.
Это прогноз контрольного прогона, а не заявление о предварительной самостоятельной работе автора отчёта.

Факт для исходного примера:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
F: задача таймера
```

С собственной микрозадачей:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: собственная микрозадача
F: задача таймера
```

A, B и C выполняются синхронно. Затем обрабатываются микрозадачи D и продолжение await E;
добавленная после синхронного кода G попадает за ними. Таймер F выполняется после микрозадач.

## HTTP-наблюдения

| Маршрут | Ожидаемый статус | Фактический статус | ok | Content-Type | Форма тела |
|---|---:|---:|---|---|---|
| `/health` | 200 | 200 | true | `application/json; charset=utf-8` | JSON: data |
| `/tasks?completed=false&priority=high` | 200 | 200 | true | `application/json; charset=utf-8` | JSON: data, meta |
| `/tasks/999` | 404 | 404 | false | `application/json; charset=utf-8` | JSON: error |
| `/debug/error` | 503 | 503 | false | `application/json; charset=utf-8` | JSON: error |
| `/debug/invalid-json` | 200 | 200 | true | `application/json; charset=utf-8` | Повреждённый JSON |
| `/debug/text` | 200 | 200 | true | `text/plain; charset=utf-8` | Обычный текст |

HTTP-статус проверяется до анализа формата успешного тела. HTTP 404 сам по себе не отклоняет fetch.
После успешного 204 возвращается null; затем для остальных успехов проверяются Content-Type и JSON.
JSON дополнительно проверяется по предметной схеме: типы полей, уникальные id, meta.total.
URL строится стандартными URL/URLSearchParams; false и 0 не теряются, null/undefined/пустая строка пропускаются.
В фильтрах допускаются только completed, priority, categoryId и q. Входные объекты не меняются.

## Виды ошибок

| kind | Причина | Реальный сценарий / проверка |
|---|---|---|
| http | Получен неуспешный HTTP-ответ | Задача 999: 404 TASK_NOT_FOUND; debug/error: 503 |
| network | Не удалось получить HTTP-ответ | Запрос после остановки API |
| invalid-response | Не Response, неверный тип или JSON/схема | debug/text и debug/invalid-json |
| timeout | Истёк установленный срок ожидания | Запрос debug/delay с коротким лимитом |
| aborted | Явная отмена AbortController | Сигнал во время запроса и до запуска fetch |

ApiError сохраняет kind, status, code, details, url и cause. Сигнал отменяет и получение ответа, и чтение тела.
Таймер и внешний обработчик сигнала освобождаются в finally.

## Ответы на контрольные вопросы

1. **Promise и значение?** Promise представляет будущий результат; само значение доступно после успешного ожидания.

2. **Три состояния Promise?** pending, fulfilled, rejected.

3. **Почему код после fetch выполняется раньше ответа?** fetch возвращает Promise и не блокирует текущий синхронный код.

4. **Микрозадача и таймер?** Продолжения Promise/await выполняются на контрольной точке микрозадач перед следующей задачей таймера.

5. **Что возвращает async?** Всегда Promise, включая случай return обычного значения.

6. **Как ошибка попадает в catch?** await отклонённого Promise выбрасывает причину отказа внутри текущей async-функции.

7. **Почему fetch не отклоняется на 404?** HTTP-ответ получен; его успешность проверяет приложение через response.ok.

8. **Что означает ok?** Статус находится в диапазоне 200–299.

9. **Почему нужно await response.json()?** Чтение тела асинхронно и возвращает отдельный Promise.

10. **Зачем Content-Type?** Проверяем, что успешный ответ объявлен JSON, прежде чем разбирать тело.

11. **Почему валидный JSON может не подойти?** В нём могут отсутствовать поля, быть неверные типы, дубликаты id или неверный total.

12. **Зачем URLSearchParams?** Для корректного кодирования параметров, включая кириллицу, пробелы и амперсанд.

13. **Почему сохраняем false?** Это значимый фильтр невыполненных задач, а не отсутствие фильтра.

14. **HTTP и network?** При HTTP есть полученный статус; при network ответа сервера не удалось получить.

15. **Тайм-аут и отмена?** Тайм-аут инициирует клиентский срок ожидания, отмену — внешний вызывающий код.

16. **Что делает AbortController?** Передаёт подписанным операциям сигнал прерывания; сама операция должна его поддерживать.

17. **Когда Promise.all?** Для независимых операций, результаты которых нужны вместе.

18. **Что при отказе одного Promise?** Общий Promise отклоняется по первой наблюдаемой ошибке.

19. **Отменяет ли Promise.all остальные?** Нет, отмену нужно организовать отдельно.

20. **Зачем два слоя клиента?** Общий слой знает HTTP, предметный — маршруты, фильтры и схемы задач/категорий.

21. **Зачем fetchFn аргументом?** Чтобы изолированно проверять ответы и ошибки без настоящей сети.

22. **Что проверяют модульные тесты?** URL, переданные параметры, преобразования, схему и классификацию ошибок.

23. **Что добавляет интеграция?** Совместимость клиента с реальными заголовками, статусами и телами готового API.

24. **Почему CORS различается?** Политику origin применяет браузер; обычный fetch Node.js её не навязывает.

25. **Что используется в ПР6?** ApiError, buildUrl, клиент с тайм-аутом/отменой и предметные методы чтения.
